# Software Supply Chain Security Checklist

**A03:2025 — Software Supply Chain Failures.** Organised by the four questions you must be able to answer:

1. **What is in it?** → SBOM
2. **Where did it come from?** → provenance & signing
3. **Should we trust the source?** → dependency governance
4. **Does this vulnerability actually affect us?** → VEX & reachability

---

## 1. What is in it — SBOM

- [ ] SBOM generated for every build artifact, automatically
- [ ] Generated **at build time from the build system**, not by scanning the finished artifact
- [ ] Format is CycloneDX or SPDX (both if you have external consumers with different requirements)
- [ ] Includes transitive dependencies, not just direct ones
- [ ] Includes OS packages for container images, not only application libraries
- [ ] Components carry PURLs and, where available, CPEs — matching quality depends on this
- [ ] SBOMs are stored in a queryable system (Dependency-Track, GUAC), not attached to a build log that expires
- [ ] Stored SBOMs are **continuously re-evaluated** against new advisories
- [ ] You can answer "which of our services ship library X version Y?" in minutes
- [ ] SBOMs are attached to artifacts as attestations, not just uploaded as files
- [ ] Retention aligns with product support lifetime (EU CRA expects this for the supported lifecycle)

## 2. Where did it come from — provenance & signing

- [ ] All release artifacts are signed (`cosign`, keyless via OIDC preferred — no key management burden)
- [ ] SLSA provenance is generated by the build platform, not by the build script
- [ ] Target SLSA Build level is defined and known (L1 → L3); the gap to the next level is a tracked item
- [ ] Provenance records: builder identity, source repo and commit, build parameters, and materials
- [ ] Signatures are logged to a transparency log (Rekor)
- [ ] **Verification happens at deploy/admission time** — signing without verification is paperwork
- [ ] Verification policy checks the *identity* of the signer, not merely that a signature exists
- [ ] Git tags and releases are signed
- [ ] Build platform is hardened: isolated builds, signing keys unreachable from user-defined steps

## 3. Should we trust the source — dependency governance

- [ ] Dependencies resolve from an internal proxy/registry, not directly from public registries
- [ ] Lockfiles with integrity hashes are committed and enforced in CI (`npm ci`, `pip --require-hashes`, `go.sum`, `Cargo.lock`)
- [ ] Internal package names are scoped/namespaced so they cannot be shadowed publicly (**dependency confusion**)
- [ ] Registry resolution order is explicit — no fallback from private to public for internal names
- [ ] Install-time scripts are disabled or reviewed (`npm ci --ignore-scripts` where feasible)
- [ ] New dependencies go through a lightweight review: maintenance activity, maintainer count, download trend, name plausibility
- [ ] [OpenSSF Scorecard](https://github.com/ossf/scorecard) runs against critical dependencies
- [ ] Automated updates (Renovate/Dependabot) are enabled **with a cooldown window** — do not adopt a version published minutes ago
- [ ] A vendoring or mirroring strategy exists for critical dependencies (protection against deletion, not just compromise)
- [ ] License compliance is checked alongside vulnerabilities
- [ ] Base images and build tool versions are pinned by digest

## 4. Does it affect us — triage

- [ ] Findings are prioritised by KEV → EPSS → exposure → reachability, not CVSS alone
- [ ] Reachability analysis is used where the tooling supports it
- [ ] **VEX documents** are produced for not-affected findings so the same CVE is not re-triaged every release (OpenVEX, CSAF, CycloneDX VEX)
- [ ] VEX statements from upstream vendors are consumed, not ignored
- [ ] There is a defined SLA per severity, and MTTR is measured against it
- [ ] Bulk remediation is preferred (upgrade the base image once, not 400 findings individually)

## Pipeline & tooling supply chain

*(Your CI is part of your supply chain — see [pipeline-security.md](pipeline-security.md) for the full list.)*

- [ ] Third-party CI actions/plugins pinned to full commit SHAs
- [ ] Build tools and container base images pinned by digest
- [ ] Nothing is `curl | bash`-ed at build time without checksum verification
- [ ] Runner egress is restricted and monitored

## Incident readiness

- [ ] You can identify every artifact containing a given component within one hour
- [ ] You can rebuild and redeploy any production artifact from source without manual steps
- [ ] A playbook exists for "a dependency we use was backdoored"
- [ ] A playbook exists for "one of our own published packages was compromised"
- [ ] Contact path exists for reporting a vulnerability to you (`SECURITY.md`, [security.txt](https://securitytxt.org/))

## Attacks this checklist is defending against

| Incident | Technique | Control that stops it |
|---|---|---|
| **SolarWinds** (2020) | Build system compromised; code injected during build | Hermetic, isolated builds + provenance (SLSA L3) |
| **Codecov** (2021) | Modified bash uploader exfiltrated CI env vars | Checksum verification of fetched scripts; runner egress control |
| **Log4Shell** (2021) | Critical flaw in a ubiquitous transitive dependency | SBOM inventory + continuous re-evaluation |
| **Dependency confusion** | Internal package name resolved from public registry | Scoped names + explicit registry precedence |
| **`xz-utils` / CVE-2024-3094** (2024) | Multi-year social engineering of maintainer trust | Scorecard signals; vendoring critical deps; reproducible builds |
| **`tj-actions/changed-files`** (2025) | Existing version tags rewritten to malicious code (~23k repos) | **SHA pinning** |
| **`Shai-Hulud` npm worm** (2025) | Self-replicating malware using stolen npm tokens to republish maintainers' packages | Install-script restrictions, cooldown windows, token scoping, 2FA on publish |

## Quick commands

```bash
# Generate an SBOM
syft myimage:tag -o cyclonedx-json=sbom.cdx.json
syft dir:. -o spdx-json=sbom.spdx.json

# Scan an SBOM rather than re-scanning the artifact
grype sbom:sbom.cdx.json
trivy sbom sbom.cdx.json

# Sign and attest, keyless
cosign sign myimage@sha256:...
cosign attest --type cyclonedx --predicate sbom.cdx.json myimage@sha256:...

# Verify signature + provenance before deploying
cosign verify \
  --certificate-identity-regexp 'https://github.com/ORG/REPO/.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  myimage@sha256:...

# GitHub artifact attestations
gh attestation verify myartifact --owner ORG

# Score a dependency's security posture
scorecard --repo=github.com/some/dependency

# Check for known-vulnerable dependencies precisely
osv-scanner scan source -r .

# Emit a VEX statement
vexctl create --product="pkg:oci/myimage@sha256:..." \
  --vuln="CVE-2024-XXXX" --status="not_affected" \
  --justification="vulnerable_code_not_in_execute_path"
```
